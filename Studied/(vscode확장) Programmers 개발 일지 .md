# Programmers Problem Helper 개발 기록

프로그래머스 문제를 풀 때마다 늘 비슷한 준비를 반복했다. 문제 페이지를 열고, 예제 입력을 확인하고, VS Code에 파일을 만들고, 테스트 코드를 대충 붙이고, 다시 웹으로 돌아가 제출했다. 한두 문제를 풀 때는 괜찮지만, 꾸준히 연습하려고 하면 이 준비 과정이 생각보다 집중력을 많이 가져갔다.

그래서 처음 만들고 싶었던 것은 거창한 서비스가 아니었다. 프로그래머스 문제 번호만 입력하면 VS Code 안에서 문제 설명과 풀이 파일이 바로 열리고, 예제 테스트를 바로 돌릴 수 있는 작은 도구였다. 알고리즘 풀이 자체에 집중하기 위해, 매번 반복하던 주변 작업을 확장 프로그램이 대신 해 주면 좋겠다고 생각했다.

이 기록은 2026년 4월 21일 첫 커밋부터 2026년 5월 4일 v0.5.2까지, 이 프로젝트가 어떤 이유로 시작했고 어떤 문제를 만나면서 기능과 구조를 바꿔 왔는지 시간순으로 정리한 글이다.

## 2026-04-21: 문제 번호에서 풀이 환경까지

처음 목표는 단순했다. VS Code Activity Bar에 `Programmers` 사이드바를 만들고, 사용자가 문제 번호를 입력하면 프로그래머스 문제 페이지를 가져와 로컬에 문제 폴더를 만드는 것이었다.

초기 구조는 지금보다 훨씬 작았다. 문제 하나는 대략 아래처럼 저장되도록 잡았다.

```text

Programmers/

<문제번호>_<문제이름>/

problem.md

solution.cpp

.programmers-helper/

programmers.json

```

`problem.md`에는 문제 설명을 Markdown으로 저장하고, `solution.cpp`에는 프로그래머스에서 제공하는 초기 C++ 템플릿을 넣었다. `.programmers-helper/programmers.json`에는 문제 URL, 예제, 메타데이터처럼 확장이 다시 읽어야 하는 정보를 보관했다.

처음부터 중요한 기준은 "내 풀이 데이터는 내 컴퓨터 안에 남아야 한다"는 점이었다. 별도 서버를 만들지 않고, VS Code 확장이 로컬 파일과 로컬 실행 환경만 다루도록 했다. 문제 페이지를 가져오는 것 외에는 풀이 코드나 테스트 입력을 외부로 보내지 않는 방향으로 잡았다.

초기 배포도 함께 정리했다. GitHub Release에서 `.vsix` 파일을 받을 수 있게 만들고, 버전 태그를 기준으로 패키징되는 흐름을 붙였다. 이때는 아직 "내가 쓰는 도구를 다른 사람도 설치할 수 있게 한다" 정도의 감각이었지만, 이후 Marketplace 배포까지 이어지는 바탕이 됐다.

## 2026-04-22: 테스트 실행이 실제 사용성을 만들었다

문제 파일을 만드는 것만으로는 부족했다. 코딩테스트 연습에서 제일 자주 하는 일은 코드를 고치고 예제를 다시 실행하는 것이다. 그래서 v0.0.5 무렵부터 테스트 실행 흐름을 본격적으로 다듬었다.

처음에는 C++ 풀이 파일을 기준으로 테스트 러너를 생성하고, 문제의 샘플 입력과 예상 출력을 케이스별로 실행했다. 이때 신경 쓴 부분은 결과를 너무 장황하게 보여주지 않는 것이었다. 전체 로그는 Output 패널에 남기되, 사이드바에서는 어떤 케이스가 통과했고 어떤 케이스가 실패했는지를 바로 볼 수 있게 했다.

또 하나 중요한 기능은 실행 중지였다. 무한 루프나 느린 코드가 생길 수 있기 때문에, 케이스별 제한 시간을 두고 사용자가 테스트를 멈출 수 있어야 했다. 여기서부터 이 확장은 단순한 파일 생성기가 아니라 "풀이 중 계속 옆에 붙어 있는 도구"에 가까워졌다.

## 2026-04-24: 커스텀 테스트와 문제 목록

샘플 테스트만으로는 부족한 경우가 많았다. 경계값이나 직접 떠올린 반례를 넣어 보고 싶을 때가 많아서, 문제별 커스텀 테스트를 저장하고 다시 열었을 때 복원하도록 만들었다.

이때부터 사이드바는 단순 입력 폼이 아니라 작은 작업 공간이 되기 시작했다. 문제 검색을 추가하고, 저장된 문제 목록에서 다시 열 수 있게 했고, 삭제도 확장 안에서 처리했다. `notes.md`를 열어 문제별 학습 메모를 남길 수 있게 한 것도 이 흐름 위에 있다.

문제 풀이 기록 기능도 들어갔다. 알고리즘 문제는 한 번 풀고 끝나는 것보다, 나중에 다시 풀어 보면서 이전 풀이와 비교할 때 얻는 게 많다. 그래서 `새풀이`를 누르면 현재 풀이를 스냅샷으로 보관하고 새로운 풀이 파일에서 다시 시작하도록 했다. 이 기능은 나중에 언어별 풀이 기록, 탭 유지 정책까지 연결되는 꽤 중요한 축이 됐다.

## 2026-04-25: Docker 실행과 런타임 분리

로컬에서 C++ 컴파일을 바로 실행하는 방식은 간단하지만, 환경 차이에 취약했다. 특히 Windows, macOS, Linux마다 컴파일러와 실행 파일 이름, 경로 처리 방식이 조금씩 달랐다. 그래서 v0.0.8에서 Docker 런타임을 도입했다.

Docker 모드에서는 확장이 helper 컨테이너를 준비하고, 그 안에서 테스트 러너를 컴파일하고 실행한다. 사용자는 VS Code 안에서 버튼만 누르지만, 내부적으로는 로컬 환경 차이를 최대한 줄이는 구조다.

이 시점에 코드도 역할별로 나누기 시작했다. 문제 저장소, 테스트 실행, Docker 런타임, 사이드바 렌더링이 한 덩어리로 섞이면 기능을 추가할수록 고치기 어려워질 게 분명했다. 그래서 "문제를 가져오고 저장하는 코드", "실행 환경을 준비하는 코드", "테스트 결과를 만드는 코드", "UI를 보여주는 코드"를 분리하려고 했다.

v0.0.9와 v0.0.10에서는 사이드바 사용성을 손봤다. 상태 섹션을 접을 수 있게 하고, 문제별 메모 파일을 추가했다. 작은 기능들이지만 실제로 매일 쓰는 도구에서는 이런 마찰이 꽤 크게 느껴진다.

## 2026-04-27: 성능과 안정성에 집중한 날

문제 수가 늘어나면 매번 폴더 전체를 훑는 방식은 느려질 수밖에 없다. v0.0.11부터 v0.0.16까지는 사이드바가 빨리 뜨고, 문제 목록이 불필요하게 다시 그려지지 않도록 만드는 데 시간을 많이 썼다.

샘플 테스트도 매번 `problem.md`를 파싱하지 않고, 저장된 `programmers.json`의 예제를 우선 사용하도록 했다. 문제 목록은 인덱스 파일로 캐시하고, 생성/삭제/다시풀기 같은 변경이 있을 때만 갱신하도록 바꿨다. Webview에서는 목록 row를 key 기반으로 재사용해 HTML 전체를 계속 새로 만드는 비용을 줄였다.

이 과정에서 에디터 레이아웃 문제도 여러 번 만났다. 문제를 바꾸거나 풀이를 초기화할 때 왼쪽의 문제 미리보기와 오른쪽의 풀이 파일이 깜빡이거나, 엉뚱한 탭이 닫히는 일이 있었다. 그래서 현재 문제의 `problem.md`와 실제 실행 대상 풀이 파일을 더 엄격하게 구분하고, generated runner 파일이 실수로 테스트 대상이 되지 않도록 경로 검증을 넣었다.

v0.0.18에서는 실행 모드 설정도 정리했다. `docker`와 `local`을 설정으로 고를 수 있게 하고, 모드가 바뀔 때 Docker 컨테이너를 정리하거나 다음 실행까지 준비를 미루는 흐름을 만들었다. 이때부터 "기능이 된다"보다 "상태 전환이 이상하지 않다"가 더 중요해졌다.

## 2026-04-28: V0.1.0, 그리고 다중 언어로 확장

v0.1.0은 첫 번째로 어느 정도 정리된 버전이었다. 기본 단축키를 추가해 `Ctrl+Alt+T`로 샘플 테스트를 실행하고, `Ctrl+Alt+S`로 실행을 중지할 수 있게 했다. VS Code 명령으로 기능을 노출했기 때문에 사용자가 직접 키보드 단축키를 바꿀 수도 있었다.

같은 날 Windows 로컬 실행 문제를 고치면서 플랫폼 차이를 다시 확인했다. Windows에서는 C++ 실행 파일이 `.exe`로 만들어져야 하고, POSIX 전용 헤더를 포함하면 안 됐다. 그래서 Windows에서는 Docker 모드를 권장하되, 로컬 모드를 쓸 경우 MinGW `g++`나 LLVM `clang++` 같은 GNU/Clang 계열 컴파일러가 필요하다고 문서화했다.

그리고 v0.2.0에서 Java 지원을 추가했다. 이때 단순히 `Solution.java` 파일만 추가한 것이 아니라, 앞으로 언어를 더 늘릴 수 있도록 구조를 바꿨다.

`src/problems/languages.js`에 언어별 파일명, 초기 템플릿 파일명, Programmers URL 파라미터, runner 파일명을 모으고, `languageRunnerRegistry`가 현재 언어에 맞는 runner builder를 선택하도록 했다. C++과 Java는 컴파일 방식도 다르고, 에러 메시지를 읽는 방법도 다르다. 그래서 언어별 차이는 builder와 formatter 쪽으로 밀어 넣고, 테스트 실행 흐름 자체는 최대한 공통으로 유지하려고 했다.

v0.2.1에서는 현재 풀이 코드를 클립보드에 복사하고 프로그래머스 웹 페이지를 여는 `웹` 버튼을 추가했다. 자동 제출까지 하지는 않았다. 제출은 사용자가 직접 하는 편이 안전하고, 확장이 웹사이트 입력을 마음대로 조작하지 않는 선을 지키고 싶었다.

v0.2.2와 v0.2.3에서는 Marketplace 배포를 준비했다. 아이콘, publisher, 키워드, README, 개인정보 안내, 면책 문구를 정리하고, 태그 배포 시 Marketplace publish까지 이어지는 workflow를 붙였다.

## 2026-04-28: Python 지원과 Runner 구조의 검증

v0.3.0에서는 Python을 추가했다. Java를 넣을 때 언어별 구조를 분리해 둔 덕분에 Python은 비교적 자연스럽게 들어갈 수 있었다.

Python은 C++이나 Java처럼 별도 컴파일이 필요 없기 때문에 생성된 `test_runner.py`가 `importlib`로 사용자의 `solution.py`를 로드하고 `solution(...)` 함수를 호출하도록 했다. 대신 런타임 오류가 났을 때 사용자가 봐야 할 위치는 generated runner가 아니라 자기 풀이 파일이어야 했다. 그래서 traceback에서 `solution.py`의 위치와 주요 예외를 요약해 보여주는 쪽을 보강했다.

이 시점에 helper 저장 구조도 정리했다.

```text

.programmers-helper/

initial/

solutions/

generated/

runners/

artifacts/

fingerprints/

```

초기 코드, 사용자가 보관한 풀이 기록, 확장이 생성한 runner와 artifact가 섞이지 않도록 분리했다. 이 구분은 나중에 Git 동기화를 넣을 때 특히 중요해졌다. 사용자가 남긴 풀이와 메모는 동기화 대상이지만, 매번 다시 만들 수 있는 generated 파일은 굳이 Git에 올릴 필요가 없기 때문이다.

## 2026-04-29: 준비 상태와 타이머

v0.3.1과 v0.3.2에서는 실행 환경 준비 상태를 더 잘 보여주도록 했다. Docker 이미지를 pull하거나 build하는 동안 지금 무엇을 하고 있는지 사이드바에 표시하고, 로컬 모드에서는 `clang++`, `g++`, `javac`, `java`, `python3` 같은 명령어가 실제로 있는지 확인했다.

그 다음 추가한 큰 기능은 문제별 타이머였다. 알고리즘 문제를 풀 때 "얼마나 걸렸는지"는 꽤 중요한 피드백이다. v0.3.4에서 시작/중지/초기화가 가능한 타이머를 넣고, 30/60/90/120분 목표 시간을 고를 수 있게 했다.

처음에는 타이머 상태를 VS Code workspace state에 저장했지만, v0.3.5에서 문제 폴더 안의 `.programmers-helper/timer.json`으로 옮겼다. 이유는 명확했다. 타이머도 문제 풀이 기록의 일부라면 문제 폴더와 함께 움직이는 편이 자연스럽다. 나중에 다른 환경과 동기화할 때도 workspace 내부 저장소에 숨어 있는 값보다 파일로 남아 있는 편이 낫다.

이때 커스텀 테스트 UI도 다시 손봤다. 저장 버튼, 저장됨/저장 필요 표시를 추가하고, 사용자가 임시로 입력 중인 값과 실제 저장된 테스트를 구분했다. 작은 상태 차이를 명확히 하는 일이 전체 사용감을 많이 바꿨다.

## 2026-04-30: 개발 환경 정리와 사이드바 UX

v0.3.6부터 v0.4.1까지는 사용성과 개발 흐름을 많이 다듬었다.

먼저 자동 업데이트 후 새 버전이 설치되면 VS Code 재로드 안내를 띄우도록 했다. 확장 업데이트는 설치만으로 끝나지 않고 창을 다시 로드해야 반영되는 경우가 있어서, 사용자가 "업데이트됐는데 왜 그대로지?"라고 느끼지 않게 하고 싶었다.

개발 환경도 정리했다. 초기에 쓰던 Dev Container와 symlink 기반 개발 흐름을 제거하고, 로컬 VS Code의 `Run Extension`을 기준으로 단순화했다. 개발 모드와 패키징 설치본을 VS Code 공식 `extensionMode`로 구분하도록 바꿨고, 개발 중에는 업데이트 재로드 알림 같은 배포판 전용 동작을 건너뛰게 했다.

v0.4.1에서는 사이드바 목록 UX를 집중적으로 고쳤다. 문제 생성 중에는 입력창과 버튼을 잠그고, 중복 생성 요청을 제한했다. 현재 열린 문제는 배경, 왼쪽 표시선, `현재` 배지로 구분했다. 필터와 검색 영역은 고정하고 문제 row만 스크롤되게 만들었다.

이런 변화들은 기능 목록으로 보면 작지만, 실제로는 "도구를 오래 켜 두고 계속 쓸 수 있는가"와 관련이 있다. 문제를 많이 풀수록 목록 스크롤 위치, 선택 상태, 필터 유지 같은 사소한 상태가 자주 눈에 밟힌다. 그래서 이 시기에는 새 기능보다 마찰 제거에 가까운 작업이 많았다.

## 2026-05-01: 다시 열었을 때의 상태

v0.4.2와 v0.4.3에서는 VS Code를 다시 열었을 때의 경험을 손봤다.

확장이 처음 활성화될 때 마지막으로 사용한 문제를 자동으로 다시 열고, 현재 로컬 또는 Docker 실행 준비 상태를 사이드바에 반영하도록 했다. 다만 Docker 모드에서는 마지막 문제를 복원했다고 해서 바로 컨테이너를 시작하지는 않았다. 컨테이너 준비는 시간이 걸릴 수 있으므로, 사용자가 실제로 문제를 열거나 테스트를 실행할 때 준비하도록 미뤘다.

이 판단은 프로젝트 전체에서 반복해서 나온 기준과도 맞닿아 있다. 사용자가 지금 하려는 행동에 필요한 만큼만 준비하고, 무거운 작업은 가능한 한 늦춘다. 사이드바 활성화, Docker 준비, 테스트 컴파일 캐시 모두 같은 방향의 설계였다.

## 2026-05-02: Git 동기화와 구조 재편

v0.5.0은 프로젝트에서 가장 큰 전환점이었다. 여러 환경에서 같은 문제 폴더와 풀이 상태를 쓰고 싶다는 요구가 생겼고, 이를 위해 Git 기반 동기화를 선택 기능으로 추가했다.

처음부터 자동으로 모든 것을 push하는 방식은 피했다. 풀이 코드는 개인 데이터이고, 충돌이 생길 수도 있기 때문이다. 대신 `Programmers: Setup Sync`로 원격 저장소와 브랜치를 설정하고, `Programmers: Sync Now`를 실행했을 때 명시적으로 저장, commit, fetch, merge, push가 진행되도록 했다.

동기화 흐름은 대략 아래 순서다.

```text

save all -> git add/commit -> fetch -> merge -> conflict marker 검사 -> push

```

HTTPS GitHub token은 VS Code SecretStorage에 저장하고, Git 명령 인자에 직접 넣지 않도록 askpass 스크립트를 사용했다. 충돌이 생기면 conflict resolver Webview를 열어 일반 파일 충돌은 VS Code의 충돌 UI로 해결하고, 삭제/수정 충돌은 문제 폴더를 유지할지 삭제를 유지할지 선택할 수 있게 했다.

이 기능을 넣으면서 `src` 구조도 크게 재정리했다.

```text

src/

core/

problems/

runners/

sync/

timers/

ui/

```

문제 명령도 CRUD, 풀이 action, 테스트 action으로 나누고, 테스트 러너도 runtime, compiler, executor, artifacts로 분리했다. 단순히 파일을 예쁘게 나눈 것이 아니라, Git 동기화처럼 부작용이 큰 기능을 넣으려면 각 모듈이 무엇을 책임지는지 분명해야 했다.

동기화 대상 정책도 이때 정리했다. `problem.md`, 풀이 파일, 메모, 타이머, 커스텀 테스트, 풀이 기록은 사용자 데이터이므로 Git에 남긴다. 반대로 `.programmers-helper/generated/`와 문제 목록 인덱스는 다시 만들 수 있는 캐시이므로 `.gitignore`에 넣었다.

v0.5.1에서는 Sync Now의 원격 통합 방식을 rebase에서 merge로 바꿨다. 로컬 풀이 커밋이 여러 개 쌓인 상태에서 rebase를 쓰면 같은 충돌을 반복해서 해결해야 할 가능성이 있었다. 풀이 기록 저장소라는 목적에는 merge가 더 덜 피곤한 선택이라고 봤다.

또 Marketplace 배포 workflow도 태그 release에서 분리했다. GitHub Release를 만드는 것과 Marketplace에 publish하는 것은 실패 지점과 권한이 다르기 때문에, 수동 실행 workflow로 나누는 편이 운영하기 쉬웠다.

## 2026-05-04: 탭 유지 정책과 설정 정리

v0.5.2에서는 에디터 탭 정리 방식을 설정으로 만들었다. 이전에는 문제나 풀이 기록을 열 때 왼쪽에는 `problem.md`, 오른쪽에는 선택한 풀이 파일만 남기는 쪽에 가까웠다. 하지만 실제로 쓰다 보면 같은 문제 안에서 현재 풀이와 풀이 기록을 번갈아 보며 비교하고 싶을 때가 많았다.

그래서 `programmersHelper.tabResetMode`를 추가했다.

- `always`: 문제나 풀이기록을 열 때마다 현재 문제와 선택한 풀이 탭만 남긴다.
- `onProblemChange`: 다른 문제로 넘어갈 때만 정리하고, 같은 문제 안의 풀이/풀이기록 탭은 유지한다.
- `never`: 문제를 바꿔도 오른쪽 풀이/풀이기록 탭을 가능한 한 유지한다.

기본값은 `onProblemChange`로 잡았다. 문제를 바꿀 때는 화면을 정리해 주는 편이 덜 헷갈리고, 같은 문제 안에서는 비교하던 탭을 살려 두는 편이 자연스럽다고 봤다.

설정 UI도 General, Test Runner, Sync 그룹으로 나눴다. 처음에는 설정이 몇 개 없어서 한 덩어리여도 괜찮았지만, 언어, 실행 모드, 타임아웃, 컴파일러, 동기화 설정이 늘어나면서 사용자가 원하는 항목을 찾기 쉽게 정리할 필요가 있었다.

## 설계하면서 계속 지키려고 한 것

이 프로젝트를 만들면서 계속 같은 기준으로 돌아오려고 했다.

첫째, 문제 풀이의 중심은 사용자의 코드다. 확장은 문제 설명을 가져오고, 파일을 열고, 테스트를 실행하고, 기록을 관리하지만 제출이나 풀이 자체를 대신하지 않는다. 그래서 `웹` 버튼도 코드를 클립보드에 복사하고 문제 페이지를 여는 선에서 멈췄다.

둘째, 사용자가 만든 데이터와 확장이 만든 생성물을 분리한다. 풀이 파일, 메모, 커스텀 테스트, 타이머, 풀이 기록은 오래 남아야 하는 데이터다. 반면 테스트 runner, 컴파일 artifact, fingerprint, 문제 목록 인덱스는 필요할 때 다시 만들 수 있는 캐시다. 이 구분을 파일 구조에 반영하면서 동기화와 삭제, 패키징이 훨씬 명확해졌다.

셋째, 무거운 작업은 늦게 하고 상태는 분명히 보여준다. 확장 활성화 시점에는 가능한 한 가볍게 시작하고, 실제 명령이나 Webview 액션이 들어왔을 때 서비스를 준비한다. Docker 컨테이너도 필요할 때 준비하고, 준비 중에는 사용자가 지금 무슨 일이 일어나는지 알 수 있게 상태 메시지를 보여준다.

넷째, 언어별 차이는 작게 가둔다. C++, Java, Python은 템플릿, 컴파일, 실행, 에러 포맷이 모두 다르다. 그래서 언어별 정의와 runner builder를 분리하고, 테스트 실행의 큰 흐름은 공통으로 유지하려고 했다. 덕분에 Java 이후 Python을 추가할 때 구조가 크게 흔들리지 않았다.

다섯째, 매일 쓰는 도구는 작은 UI 상태가 중요하다. 문제 목록 스크롤, 현재 문제 표시, 풀이 기록 선택 상태, 탭 유지 방식, 커스텀 테스트 저장 표시 같은 것들이 겉으로는 사소해 보여도 실제 사용 중에는 계속 손에 닿는다. 후반부로 갈수록 이런 부분을 고치는 시간이 늘어난 것도 그 때문이다.

## 지금 상태

현재 v0.5.2 기준으로 Programmers Problem Helper는 문제 생성, Markdown 미리보기, C++/Java/Python 풀이 템플릿, 샘플/커스텀 테스트 실행, 풀이 기록, 메모, 타이머, Marketplace 배포, Git 동기화까지 갖춘 VS Code 확장이 됐다.

처음에는 "문제 번호를 넣으면 파일을 만들어 주는 도구"였지만, 만들다 보니 실제 알고리즘 연습 과정 전체를 조금씩 품게 됐다. 문제를 가져오고, 풀고, 테스트하고, 다시 풀고, 기록하고, 여러 환경에서 이어서 작업하는 흐름까지 연결됐다.

아직 더 할 일은 많다. 더 많은 언어를 지원할 수도 있고, 테스트 결과 UI를 더 읽기 쉽게 만들 수도 있고, 동기화 충돌 경험을 더 부드럽게 만들 수도 있다. 그래도 지금까지의 방향은 꽤 분명하다. 이 확장은 알고리즘을 대신 풀어 주는 도구가 아니라, 사람이 문제를 푸는 동안 반복 작업과 환경 차이를 조용히 줄여 주는 도구로 계속 다듬어 가고 싶다.
